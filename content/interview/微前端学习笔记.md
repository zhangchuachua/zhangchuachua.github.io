## 为什么 micro-app 和 qiankun 需要子应用打包为 umd 模式？

> micro-app 可以不使用 umd 模式，但是推荐使用，参考[官方文档](https://jd-opensource.github.io/micro-app/docs.html#/zh-cn/umd)

打包完成后 umd 格式的代码示例为：

```js
;(function umd(root, factory) {
	
	if (typeof exports === 'object' && typeof module === 'object')
		// 兼容 commonjs 规范
		module.exports = factory();
	else if (typeof define === 'function' && define.amd) 
		// 兼容 amd 规范
		define([], factory);
	else if (typeof exports === 'object') 
		// 兼容 cmd 规范
		exports['name'] = factory();
	else
		// 都不属于，就直接放到全局对象中去
		root['name'] = factory();
})(window, function() {
	return {
		a: 1,
		b: 2
	}
})
```

在微前端中自然不需要考虑其他的规范，所以子应用相关的方法都会直接放到 window 上去；然后又因为 qiankun 和 micro-app 的流程是：

1. 先加载 html
2. 提取出 script 标签
3. 在沙盒中执行 js 代码

所以子应用中的 mount, unmount 等函数都将会被挂载到沙盒的 window 对象上。

> [!tip] micro-app 没有使用导出，而是直接使用 `window.mount = () => {}` 这样直接把方法绑定到 window 上，其实与 qiankun 的导出没有区别。

## 如何处理在 document.body 上添加事件的情况？

使用事件劫持的方式，劫持所有的 `addEventListener` 当执行 `addEventListener` 时，就获取对应的回调函数，当子应用卸载时就去 remove

其实这个问题，应该是在子应用内部进行处理的，比如 vue 组件内部的 mounted 进行事件添加，unmounted 进行事件移除，所以这个问题其实不太常见。

### qiankun

qiankun 只劫持了 window 上的 addEventListener 所以如果是通过 window.addEventListener 添加的事件不需要管理，qiankun 会自动销毁事件。

但是如果使用了 document.body.addEventListener 那么就需要在 unmount 中手动进行销毁。

> qiankun 使用 proxy 包装了 window 

### micro-app

针对于 window 和 document 上的 addEventListener 都进行了劫持，但是并没有劫持元素的 addEventListener 所以事件依然会添加到 document.body 上。所以可以在子应用的生命周期中进行移除

> micro-app 对 window 和 document 都使用了 proxy 进行包装
> 
> 但是打印 document.body 获取到的依然是全局的 body
> 
> 但是 micro-app 又劫持了 appendChild 所以如果使用 `document.body.appendChild` 在子应用中添加节点的话，那么将会添加到子应用的 body 中。

## js 沙箱如何实现的？

### qiankun 

仅仅实现了 with 沙箱，具体的实现参考：[微前端原理-沙盒](https://www.bilibili.com/video/BV1T5411m7jP/)

大概原理就是：

```js
const proxyWindow = new Proxy(window, {
	get(...) {...},
	set(...) {...}
});

function execCode(code, fakeWindow) {
	window.proxy = fakeWindow;
	const _code = `;(function(window) {
		// 这里的 window 就是 window.proxy 也就是 proxyWindow
		// 所以下面的代码，都将会在 proxyWindow 下执行，with 语法就是让下面的代码，在 proxyWindow 上查找变量；
		with(window) {
			${code}
		}
	}).call(window.proxy, window.proxy)`;
	eval(_code);
}

execCode(code, proxyWindow);
```

### wujie

wujie 使用的是 iframe 天然实现了样式和 javascript 的隔离；

wujie 将会创建一个 iframe 并且在这个 iframe 中加载并执行 js 代码，iframe 天然就是隔离的，所以不需要 js 沙箱。

但是 wujie 中子应用的 css 和具体的 html 都会放在 shadow-dom 中。

也就是说 wujie 分成了两个部分：

1. shadow-dom 加载 css 和 html 展示
2. iframe 加载执行 js

### micro-app 

micro-app 支持上面说的两种方式：

1. with 沙箱，默认
2. iframe 沙箱

```html
<micro-app iframe></micro-app>
```


## iframe 沙箱是如何实现的？

在这里只介绍 wujie 的大概的实现，micro-app 应该是差不多的。

首先是使用 iframe 沙箱时的 html 格式：

![[wujie-iframe-sandbox-html.png|wujie iframe 沙箱的 html 格式]]

![[micro-app-iframe-sandbox-html.png|micro-app iframe 沙箱的 html 格式]]

通过上面两个图片显示可以发现：

1. iframe 沙箱将会创建一个 iframe 但是 iframe 只用于加载和执行 script
2. 具体的 html 内容和 style 样式都在 web component 中

那么这是如何实现的呢？

注意 iframe 的 src 是父应用的网址，而不是子应用的网址，说明这个 iframe 就是一个同源的 iframe。

父应用可以访问和操作同源 iframe 的 html 元素，并且 wujie 和 micro-app 都劫持了 iframe 的 document 

如果通过 `iframe.contentDocument.body` 获取到的将会是 web component 中的 body； 

如果通过 `iframe.contentDocument.head` wujie 获取到的将会是 web component 中的 head；micro-app 获取到的是父应用的 head

> 注意：即使是同源的 iframe 样式也是隔离的，父应用的 css 不会做用到 iframe 中，iframe 中的样式也不会影响到父应用

## 为什么不直接使用 iframe

1. 路由状态丢失，刷新一下，iframe 的 url 状态就丢失了
2. 性能问题，每个 iframe 都会完整子应用所有的资源，可能会导致重复加载相同的资源，比如共用的依赖等
3. dom 割离严重，比如弹窗只能在 iframe 内部展示，无法覆盖全局
4. web 应用之间通信非常困难，使用 postMessage 只能传递可以序列化的数据
5. iframe 对 seo 不是太友好
6. 等

## 针对 iframe 的一些疑问

以下内容主要来自于 AI：

### iframe 会分配独立的渲染线程吗？

现代浏览器中，同站点的 iframe 会共享主线程，但是 iframe 依然独立拥有下面的内容：

1. DOM iframe 有自己的 DOM 树。
2. javascript 上下文，保证了 js 代码互相独立
3. 样式和 css
4. 历史记录

 不同域的 iframe 将会分配独立的线程（现代浏览器）

### iframe 如何分配主线程？会不会 iframe 给父窗口让行？

iframe 与父窗口会共享事件循环，所以不会去特殊处理，而是使用事件循环。

每次循环之后就会的渲染（layout，render）阶段都是统一更新的，包含了父窗口和 iframe 所以渲染也不会进行特殊处理。

## 样式隔离如何实现的？

### qiankun

qiankun 的样式隔离会有问题，参考：[zhihu](https://zhuanlan.zhihu.com/p/596349482)

![[qiankun-css-sandbox.png]]

1. 默认情况下 qiankun 仅仅使用一个 qiankun-head 存放子应用的样式，也就是说，挂载子应用时加载样式，卸载子应用时移除样式；

2. 当开启了 `sanxbox.strictStyleIsolation: true` 时 

![[qiankun-css-sandbox-shadow-dom.png]]

qiankun 使用了 shadow-dom 这样父应用的样式不会影响到子应用，然后子应用的样式也不会影响到父应用。

但是不知道为什么，qiankun 明明已经劫持了 `document.body.appendChild` 但是在子应用中使用 `document.body.appendChild` 还是可以将元素插入到父应用的 body 中，这样就导致了一些子应用的弹窗没有了样式。

3. 当开启了 `sandbox.experimentalStyleIsolation: true` 后

![[qiankun-css-sandbox-experimentalStyleIsolation.png]]
qiankun 将会在 container 上加上 `data-qiankun='name'` 然后在下面的元素中使用 `[data-qiankun='name']` 选择器其实类似于 vue 的局部 css 的做法，但是对于子应用添加到 document.body 中的弹窗依然无效。

注意这样的方法 父应用中的样式将会影响到子应用

### micro-app

1. 默认使用 qiankun 中第 3 点的做法，但是 micro-app 在子应用中使用 `document.body.appendChild` 时将会追加到子应用的 `micro-app-body` 中去

![[micro-app-css-sandbox.png]]

2. 还可以使用 shadowDOM 开启 shadow-dom 功能，但是使用不太多，在我测试的时候也遇到了问题，先忽略。

### wujie

wujie 直接使用了 shadow-dom 的样式隔离，同时子应用使用 `document.body.appendChild` 也会添加到 wujie-app 中

## qiankun 为什么不支持 vite？ 为什么 micro-app 和 wujie 使用 iframe 可以支持 vite？ 

### qiankun

因为 vite 在开发环境下使用的是 ESM 模块，比如说子应用的 `main.ts` 如下所示：

```js
import { debounce } from 'lodash-es';
```

像这种代码，在开发阶段是不会被 vite 打包成 umd 格式的，所以依然是使用 `<script type="module" src="main.js" />` 这样进行加载。

最开始 qiankun 的 import-html-entry 直接会忽略到带有 `type="module"` 的 script ，见[issue](https://github.com/umijs/qiankun/issues/507)， 后面才添加了支持。

但是即使支持了也没用，因为 qiankun 将会使用 `eval`  支持子应用的 js 代码，如果是 vite 的话，那么就会有 import ，而 import 在 eval 中执行的话会报错。

> [!tip]- 社区的解决方法
> 
> 1. vite 组件 [`vite-plugin-qiankun`](https://github.com/tengmaoqing/vite-plugin-qiankun) 但是这个项目也已经无人维护了，看了一下应用这个插件后，script 都没有 module 了 不知道具体进行了什么操作。貌似
> 2. 在生产环境接入，开发环境不行：[issue#comment](https://github.com/umijs/qiankun/issues/1268#issuecomment-807954544)

single-spa 可以支持 vite ，这是因为它不会去使用 eval 执行子应用的代码，而是使用 `import()` 加载执行子应用的代码。它并不追求全局的沙箱隔离

而 qiankun 为了实现沙箱隔离，不得不自己执行 js 代码。


### micro-app 和 wujie

micro-app(iframe 模式) 和 wujie 使用 iframe 去加载执行 module script 没有任何问题。iframe 实现了完美的 js 隔离。

## 如何父子应用通信

### qiankun

1. 加载子应用时使用 props 传递

```js
registerMicroApps([
	{
		name: "vue2",
		entry: "//localhost:7000",
		container: "#vue2-container",
		props: {
			userInfo: { name: "xxx" }
			sendMessage: (msg) => console.log('父应用收到子应用消息:', msg)
		}
	}
])
```

2. 使用 `globalState` 详细内容见[文档](https://qiankun.umijs.org/zh/api#initglobalstatestate)
	注意，globalState 不需要再传递给 props 了，执行 `initGlobalState` 后，每个子应用的 props 中都可以拿到。

### micro-app

详细内容请见[文档](https://jd-opensource.github.io/micro-app/docs.html#/zh-cn/data)

主应用向子应用发送数据：

1. 使用 data 属性发送数据：

```jsx
// data只接受对象类型，数据变化时会重新发送 
<micro-app name='appName' url='xx' data={{ msg: "hello" }} />
```

2. 使用 setData 发送数据

```js
import microApp from '@micro-zoe/micro-app' 
// 发送数据给子应用 micro-name，setData第二个参数只接受对象类型，第三个参数是回调函数将会在数据发送完成后执行
// 注意回调函数是有参数的，参数来源见文档
microApp.setData('appName', { msg: 'hello' }, (res) => {console.log("数据发送完成")})
```

注意： micro-app会遍历新旧值中的每个key判断值是否有变化，如果所有数据都相同则不会发送（注意：只会遍历第一层key），如果数据有变化则将**新旧值进行合并**后发送。

---

子应用获取来自主应用的数据：

1. 子应用中使用 `window.microApp.getData()`
2. 子应用中绑定监听函数 `window.microApp.addDataListener(dataListener: (data: Object) => any, autoTrigger?: boolean)`

---

子应用向父应用发送数据

1. 使用 dispatch, `widow.microApp.dispath({ msg: 'world' }, (res) => { console.log('数据发送完成') })` 最后一个函数也是回调函数
	注意，回调函数是有参数的，参数来源见文档
2. 使用 forceDispatch，`window.microApp.forceDispatch({ name: 'world' }, () => { console.log('数据发送完成') })`

---

父应用接收子应用发送的数据

1. 使用 getData: `microApp.getData(appName)`
2. 监听自定义事件

```jsx
// 数据在event.detail.data字段中，子应用每次发送数据都会触发datachange
<micro-app name='my-app' url='xx' onDataChange={(e) => console.log('来自子应用的数据：', e.detail.data)} />
```

3. 绑定监听函数

```js
import microApp from '@micro-zoe/micro-app'

/**
 * 绑定监听函数
 * appName: 应用名称
 * dataListener: 绑定函数
 * autoTrigger: 在初次绑定监听函数时如果有缓存数据，是否需要主动触发一次，默认为false
 */
microApp.addDataListener(appName: string, dataListener: (data: Object) => any, autoTrigger?: boolean)

// 解绑监听指定子应用的函数
microApp.removeDataListener(appName: string, dataListener: (data: Object) => any)

// 清空所有监听指定子应用的函数
microApp.clearDataListener(appName: string)
```

---

清空数据：由于通信的数据会被缓存，即便子应用被卸载也不会清空，这可能会导致一些困扰，此时可以主动清空缓存数据来解决。

1. 使用 clear-data: `<micro-app clear-data></micro-app>`
2. 使用 clearData: `microApp.clearData(appName)`

---

全局数据通信

1. 设置值：`microApp.setGlobalData({msg: 'hello'}, (res) => console.log('数据发送完成'))`
2. 获取值
	1. 事件绑定： `microApp.addGlobalDataListener((data) => console.log('全局数据', data))`
	2. 使用 getGlobalData: `microApp.getGlobalData()`
3. 清空值： `microApp.clearGlobalData()`

## 子应用路由跳转怎么处理？

### qiankun

使用 baseRoute 进行区分，主应用设置：

```js
registerMicroApp([
	{
		name: 'reactApp',
		entry: '//localhost:3000',
		container: '#react-container',
		activeRule: '/app-react'
	}
])
```

子应用设置：

```jsx
<BrowserRouter basename={window.__POWERED_BY_QIANKUN__ ? '/app-react' : '/'}>
</BrowserRouter>
```

### micro-app

详情见[文档](https://jd-opensource.github.io/micro-app/docs.html#/zh-cn/router)

#### search 模式 默认就是 search 模式

配置为：

```jsx
<micro-app name="childApp-vue2" url="//localhsot:8080" baseroute="/app-vue2" router-mode="search" />
```

url 为: `http://localhost:5173/app-vue2?childApp-vue2=/about`

使用把子应用的路径放到 search 中去，就不需要对子应用进行额外的配置了。

#### native 模式

与 qiankun 的路由一样，需要对子应用进行配置, 为子应用的路由配置 baseroute

#### native-scope 模式 

native-scope模式的功能和用法和native模式一样，唯一不同点在于native-scope模式下子应用的域名指向自身而非主应用。

假设父应用的路径为 `//localhost:5173` 子应用的路径为 `//localhost:8080` 那么：

- native 模式下，子应用中的 `location.origin` 将会为 `//localhost:5173`
- native-scope 模式下，子应用中的 `location.origin` 将会为 `//localhost:8080`

也就是说

#### pure 模式

子应用路由 **完全不影响主应用 URL**。无论子应用如何跳转，主应用 URL 保持不变。例如：  
`http://localhost:5173`（子应用内部路由为 `/child-path`）。

- 子应用路由通过内存或 Hash 路由管理，不修改浏览器 URL。
- 主应用完全感知不到子应用的路由变化。
- 缺点：用户无法通过 URL 直接访问子应用特定页面。

#### state 模式

URL 保持不变，子应用路由信息存储在 **`history.state`** 中。例如：  
`http://localhost:5173`，但 `history.state` 包含信息，假设信息为 `{ "app-vue2": "/child-path" }`。子应用就可以通过 history.state 对应的路径。与 iframe 类似，但是不会有 iframe 的问题。

- 子应用路由变化时，通过 `history.pushState/replaceState` 更新状态。
- 主应用通过监听 `popstate` 事件获取子应用路由状态。
- 优点：URL 简洁，适合不希望暴露子应用路径的场景。

详情请见[文档](https://wujie-micro.github.io/doc/guide/#%E8%B7%AF%E7%94%B1%E5%90%8C%E6%AD%A5%E6%9C%BA%E5%88%B6)

### 劫持路由

劫持路由变化

1. hash 路由

```js

const originHashChange = window.hashChange;

window.hashChange = function (...args) {
	// 劫持操作
	originHashChange.apply(this, args);
}
```
2. history 路由: 
	1. `history.go, history.back, history.forwark` 这三个函数跳转，劫持 `window.onpopstate` 
	2. `history.pushState, history.replaceState` 这两个函数，需要针对这两个函数进行劫持。
